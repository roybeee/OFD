# ODA 인사관리 구현 범위와 사용 순서

검토 기준: 2026-09-15 구현 소스. 이 문서는 실제 도메인 명령, API와 React 화면을 대조한 구현 설명이다. FLEX 조사 문서의 수나 화면 이름을 구현 기능 수로 환산하지 않았다. 실서비스 배포 성공이나 모든 FLEX 기능의 동등 구현을 의미하지 않는다. 개인정보와 실제 직원 자료는 포함하지 않았다.

## 1. 현재 결과

ODA 인사관리는 매장별 직원·조직, 근무·휴가·교대, 결재·비용 청구, 급여, 목표·평가·미팅, 채용 단계, 계약 기록, 문서와 공지를 저장하고 처리한다. 로그인한 계정, 선택한 매장, 업무 대상과 상태에 따라 서버가 조회·변경 범위를 제한한다.

직원 전용 화면과 출퇴근 위치 설정은 [직원 화면 사용 안내](oda-staff-workspace.md)를 따른다. 위치 기반 등록도 로그인한 본인과 매장 배정을 서버에서 확인한다.

기존 ODA 사용자 계정·매장·권한·영속 저장소를 이용한다. FLEX 데이터 가져오기, FLEX API 호출, 외부 전자서명, 금융기관 수집, 세무 신고, 보험 가입, 음성 요약은 HR 모듈에 연결되지 않았다. **FLEX 전체 기능의 재현 완료로 표시할 수 없다.**

| 집계 대상 | 실제 소스에서 확인한 수 | 해석 |
|---|---:|---|
| 인사관리 탭 | 16 | 아래 메뉴 표의 화면 진입점 |
| HR 명령 종류 | 97 | 명령 허용표와 실제 처리 분기를 대조한 고유 문자열 수 |
| UI에 호출 경로가 있는 명령 종류 | 95 | `workspace.initialize`, `payroll.delete`는 화면 버튼 없음. 한 명령의 모든 입력 변형이 UI에 있다는 뜻은 아님 |
| 기본 HR API | 2 | 매장별 조회 GET, 명령 POST. 개별 기능 수와 다름 |
| 급여→월정산 연결 API | 2 | 합계 미리보기 GET, 명시적 반영 POST. 기본 HR 명령 97개와 별도 |
| 공개 도메인 함수 | 25 | 주 도메인 5개 파일의 `export function`; 타입·상수·테스트·유틸 제외 |

확정 급여 인건비는 **미리보기 후 명시적 반영**으로 기존 월정산에 연결한다. 연결 API와 UI를 소스에서 확인했으며 상세 동작과 제한은 8절에 기록했다. 기본 HR 2개와 연결 2개를 합쳐 HTTP 메서드·경로 조합은 4개다.

## 3. 관리자 초기 사용 순서

1. **매장과 계정 확인.** 기존 ODA 계정에 인사관리 페이지와 매장 접근이 허용되어 있어야 한다. HR 직원 등록은 로그인 계정 생성이나 초대 메일 발송을 대신하지 않는다.
2. **조직 생성.** 직원·조직 → 조직도에서 조직과 상위 조직을 만든다. 조직장은 직원을 등록한 후 지정할 수 있다. 조직 없이 직원을 먼저 등록하는 것도 가능하다.
3. **직원 등록·연결.** 사번, 이름, 입사일, 소속, 고용형태, 월급/시급과 기본금액을 입력한다. 기존 활성 ODA 계정을 직원에 연결한다. 사번과 연결 계정은 매장 인사관리 안에서 중복할 수 없다.
4. **근무 정책 배정.** 근무 기록에서 유형·일정·휴게·소정시간·근무요일·승인 여부를 정하고 직원별 적용일을 등록한다. 설정 탭의 기본값 변경만으로 기존 정책이 변경되지는 않는다.
5. **회사 휴일·휴가 지급.** 회사 휴일 날짜 목록을 저장한다. 필요한 휴가 종류를 만들고 직원별 분 단위 잔액과 유효기간을 지급한다. 기본 연차 일수를 저장해도 잔액이 자동 발생하지 않는다.
6. **교대 일정 게시.** 근무 일정에서 근무·휴무 템플릿을 만들고 날짜별 초안을 배정한다. 선택한 초안을 게시해야 직원에게 보인다. 게시 일정 자체는 실제 근무 실적으로 계산되지 않는다.
7. **결재 양식 준비.** 로그인 계정이 연결된 재직 직원 또는 허용된 관리자 계정으로 순차 결재 단계를 구성한다. 각 단계는 전원 승인 또는 한 명 승인이다. 양식 변경은 이미 생성한 문서의 단계 스냅샷을 바꾸지 않는다.
8. **공지·규정 안내.** 공지는 게시 상태에서 직원에게 보인다. 문서는 대상을 선택하거나, 회사 규정에서 대상 미지정으로 전체에 공개한다.

설정의 `workdayHours`, `weeklyDays`, `annualLeaveDays`는 새 근무 정책·수동 휴가 지급 폼의 초기 제안에도 연결한다. 하루 시간은 분으로 환산하고, 요일은 월요일부터 주 근무일 수만큼 제안하며, 휴가 지급량은 `연차 일수 × 하루 시간 × 60`분으로 제안한다. 사용자는 수정 후 저장·배정해야 한다. 휴게·종료 시간도 수정 가능한 제안이다. 설정 변경만으로 기존 정책·휴가 잔액·급여가 바뀌지 않는다. `approvalEmployeeId`를 실제 근태 승인자로 자동 배정하는 호출은 없으며 근무·휴가 승인은 관리자 권한으로 처리한다.

적용 근무 정책과 게시 교대가 없을 때 휴가는 월~금, 09:00~18:00, 하루 최대 480분을 기준으로 검증한다. 이 기본값이 회사 설정의 하루 시간으로 자동 대체되지는 않는다.

## 4. 일상 업무와 월말 처리

### 직원

자신의 계정이 연결된 후 근무 기록에서 출근·퇴근한다. 서버 시각을 타각 원본으로 남긴다. 별도 수동 근무 입력은 실제 일자·시작·종료·휴게를 입력하고 승인 상태를 확인한다. 휴가는 지급 잔액과 근무일에 맞춰 날짜·시간·분량을 신청한다. 승인 대기 신청도 잔액을 예약한다.

전자결재는 양식 선택 → 초안 작성 → 문서 열기 → 결재 제출 순서다. 비용은 비용 초안을 만들고, 동일 금액의 본인 결재를 제출한 후 연결하여 제출한다. 현재 단계의 결재자 또는 유효한 대결자는 승인·반려할 수 있다. 반려된 결재 문서를 다시 제출하는 명령은 없으므로 새 결재 문서가 필요하다. 비용은 반려·회수 후 다시 작성하여 수정하고 연결할 수 있다.

### 관리자·급여 담당자

1. 대기 근무·휴가를 처리한다. 미퇴근 타각이 있으면 실제 퇴근을 처리하거나 사유와 함께 미퇴근을 정리하고 실제 근무를 따로 기록한다.
2. 기간과 대상을 지정해 근태를 마감한다. 미처리 근무·휴가, 미퇴근, 기존 마감 중첩, 미래 기간이 있으면 차단된다.
3. 급여에서 귀속월·지급일·월급 부분월 계산 방식을 선택해 초안을 만든다. 월별 한 건만 가능하다.
4. 대상과 기본급 계산 구간을 확인한다. 수당·일반 공제·월급제 무급휴가 공제를 직접 추가한다. 소득세·지방소득세·근로자 보험·회사 보험을 확인한 값으로 입력한다. 해당 없음도 0원을 입력하고 확인 표시한다.
5. 인사·근태가 바뀌었다면 최신 인사·근태 반영을 실행한다. 원천 변경 시 수동 확인이 해제되므로 다시 검토한다. 휴직자의 지급기준은 검토 메모에 기록한다.
6. 검토 완료 → 확정·잠금 → 명세서 공개를 실행한다. 공개 시각을 지정할 수 있다. 예약 공개는 조회 시각을 기준으로 본인 명세를 제공하며 메일이나 푸시를 보내지 않는다.
7. 정정 시 급여 수정 재개 사유를 남긴다. 기존 확정본은 이력에 보존되고 직원 공개는 철회된다. 근태를 고치려면 급여를 먼저 재개하고 근태 마감을 해제한 후 정정·재마감·급여 갱신·재검토·재공개한다.
8. 확정 또는 공개한 급여의 **월 정산 인건비 미리보기**를 열어 총 지급·회사 보험·합계·현재 반영액·중복 인건비를 확인한다. 차단 사유가 없으면 **월정산 인건비에 반영**을 누른다. 기존 월정산에서 인건비 합계 한 줄을 확인한다. 이후 급여를 재개·정정해도 기존 월정산 금액은 자동 변경되지 않으며 재확정 후 다시 반영해야 한다.

급여 계산 상세는 [급여 구현 범위](hr-payroll-implementation.md)를 참조한다. 자정 교차 근무의 급여 시간은 근무 시작일에 전량 귀속한다. 시급은 승인 인정근무와 승인 유급휴가 분을 합산하며, 월급은 적용일별 단가와 재직기간으로 계산한다. 법정 수당·세금 자동 계산으로 해석해서는 안 된다.

### 평가·미팅·채용·계약

- 평가는 관리자 준비 → 시작 → 배정받은 직원 답변 저장·제출 → 전체 제출 후 관리자 마감 → 개인 결과 공개 순서다. 기간 안에 제출 회수와 수정이 가능하다. 현재 문항은 1~5점 정수와 의견이며 결과는 단순 평균이다.
- 미팅은 자신의 직원 연결이 필요하다. 참여자는 공동 노트와 할 일을 수정하고, 개인 메모는 작성자에게만 반환한다. 관리자라도 참여하지 않은 미팅이나 다른 사람의 개인 메모를 열람하지 못한다.
- 채용은 내부 공고를 모집 중으로 전환한 후 지원자를 직접 등록한다. 합격 상태로 옮겨도 직원이 자동 등록되거나 계약이 자동 생성되지 않는다.
- 계약은 외부에서 체결한 근거를 기록하여 완료한다. 완료 자체는 전자서명이 아니며 인사정보도 즉시 바뀌지 않는다. 관리자가 적용일 이후 별도 반영 버튼을 누르면 해당 계약 조건을 한 번 반영한다. 미래 계약의 자동 실행 작업은 없다.

## 7. 데이터·API·동시 저장

HR 저장 단위는 매장당 `HrWorkspace` 한 건이며 식별자는 `hr:<storeId>`다. 직원, 조직, 설정, 공지, 문서, 근태, 급여, 성장, 결재 상태가 같은 객체에 담긴다. 직원·정책·근태·결재·급여 간 ID 연결은 이 매장 안에서 이루어진다. 본사 화면에서 매장을 바꾸는 기능이 법인 간 겸직·전배·합산 원장을 구현한 것은 아니다.

기본 API는 다음과 같다.

| 메서드·경로 | 계약 |
|---|---|
| `GET /api/v2/oda/:storeId/hr` | 접근 범위 검증 후 현재 역할에 맞게 필터한 워크스페이스·권한·본인 직원 ID 반환. 관리자에게만 연결 가능한 기존 계정 목록 반환 |
| `POST /api/v2/oda/:storeId/hr/commands` | `{expectedVersion, type, input}`와 중복 요청 키 사용. 매장 잠금 안에서 버전 확인·명령 권한·대상·상태 검증 후 저장 |

다른 요청이 먼저 저장했으면 409 충돌로 거부한다. UI는 충돌 시 최신 정보를 다시 불러오고 사용자가 입력을 확인해 재시도하게 한다. 같은 요청 재시도 캐시에 개인정보가 포함된 전체 응답을 저장하지 않고, 현재 권한으로 응답을 다시 투영한다. 조회만으로 가짜 직원·근무 기록을 생성하지 않는다. 첫 변경부터 저장한다.

기본 HR 명령 경로의 저장 제한은 직원 5,000명, 조직 500개, 공지 1,000개, 문서 2,000개와 전체 워크스페이스 직렬화 30MiB다. 공통 명령 변경 타임라인은 마지막 1,000건을 유지하며 입력 내용 대신 명령 종류를 남긴다. 이것을 무제한 감사 원장이나 파일 저장소로 해석하면 안 된다. 전체 객체를 조회·전송하는 구조이므로 대규모 가맹점 본사 통합 검색·장기 원장·페이지별 서버 조회는 후속 과제다.

## 8. 기존 월 손익·정산과 연결

### 현재 기본 HR 모듈에서 확인한 내용

HR 비용의 `evidenceNote`는 영수증 번호·파일명·보관 위치를 적는 텍스트다. HR 화면에 원본 업로드 기능은 없고 기존 월 손익·정산으로 이동하는 링크가 있다. HR 비용 검토가 완료되어도 기존 월정산 비용 행을 생성하지 않는다.

급여 계산의 인건비는 `총 지급 + 회사 부담 보험`이다. 근로자 세액·보험 공제를 인건비에 다시 더하지 않는다. `getHrPayrollFinalizedTotal`은 잠금/공개 상태 급여의 월 합계를 반환하는 함수이며, 이 함수만으로 기존 월정산에 쓰지는 않는다.

### 구현된 급여 합계 연결

급여 탭의 확정/공개 건 → **월 정산 인건비 미리보기** → 귀속월·총 지급·회사 보험·반영 합계·기존 HR 인건비·다른 인건비 확인 → **월정산 인건비에 반영** 순서다. 처리 후 최신 HR 정보를 다시 조회한다. 충돌한 미리보기는 버리고 다시 확인하게 하며 변경 요청을 조용히 재시도하지 않는다.

| 메서드·경로 | 실제 계약 |
|---|---|
| `GET /api/v2/oda/:storeId/hr/payroll-cost?month=YYYY-MM` | 합계와 HR/월정산 버전, 급여 정산 ID·상태, 기존 반영액, 다른 인건비 수·합계, 차단 사유, 이미 반영 여부 반환 |
| `POST /api/v2/oda/:storeId/hr/payroll-cost` | `month`, `expectedHrVersion`, `expectedOdaVersion`, 선택적 `expectedPayrollRunId`와 중복 요청 키. 확인한 두 저장소 버전을 검사한 뒤 원자적으로 저장 |

- 점주·본사 관리자·본사 재무는 인사관리와 월정산 접근을 모두 가져야 한다. 감사는 합계 조회 API만 허용되며 직원별 급여 행은 받지 않는다. 일반 직원은 연결 API 접근 대상이 아니다.
- 해당 귀속월의 급여가 한 건이고 확정·잠금 또는 공개 상태여야 한다. 미검토 행, 미입력 결과, 빈 급여를 차단한다. 대상 월정산은 작성 중이어야 하며 확정·지급 완료 상태는 변경하지 않는다.
- 월정산에는 고정 식별자 `hr-payroll:<month>`의 `expense`·`labor` 행 한 줄을 생성하거나 갱신한다. 금액은 총 지급과 회사 부담 보험의 합계다. 직원 이름이나 직원별 급여 행은 전달하지 않는다.
- 귀속월·합계 금액·급여 정산 ID·확정 버전만 담은 CSV 합계 증빙을 추가한다. 기존 월정산 행·원본·이전 합계 증빙은 보존한다. 해당 HR 소유 행만 갱신한다.
- 다른 인건비 행이 있으면 중복 위험을 표시하고 반영을 차단한다. 기존 HR 행·연결 원본이 수정되었거나 같은 식별자가 충돌하는 경우도 자동 덮어쓰지 않는다. 월정산 5,000행·원본 10MiB 제한도 확인한다.
- 같은 확정급여가 이미 반영되었으면 추가 행·증빙을 만들지 않는다. 공개 여부만 바뀌는 것은 별도 인건비로 중복 반영하지 않는다. HR과 월정산을 함께 잠그고 두 버전을 저장 시 검사한다.
- 급여 수정 재개가 이전 월정산 인건비를 지우지는 않는다. 정정 급여를 다시 확정한 뒤 미리보기·반영을 실행하면 같은 HR 행을 새 합계로 갱신하고 이전 증빙은 남긴다. 월정산이 이미 확정·지급 완료라면 연결 경로에서 정정할 수 없다.

근거: [연결 API](../apps/api/src/oda-hr-payroll-cost.ts), [서버 등록](../apps/api/src/app.ts), [클라이언트 호출](../apps/web/src/api/oda-hr-client.ts), [급여 화면](../apps/web/src/hr/HrPayroll.tsx). `payroll.costApplied`는 이 연결이 남기는 이력 이벤트이며 기본 `/commands`에서 허용하는 새 명령이 아니다. HR 비용 청구의 월정산 반영이나 은행 지급까지 구현한 것은 아니다.

## 10. 외부 연결 여부

| 대상 | HR 모듈의 실제 연결 상태 |
|---|---|
| 기존 ODA 로그인·계정·매장·페이지 권한 | 연결됨. 기존 사용자·매장 저장소를 조회하고 범위 검사 |
| 기존 ODA 영속 저장·감사 | 연결됨. `oda_hr` 객체 저장과 명령 감사 기록 |
| 기존 ODA 월정산 비용·증빙 | 화면 이동 링크. HR 비용 자료의 자동 복제/원본 첨부 연결 없음 |
| 기존 ODA 월정산 급여 인건비 | 연결됨. 확정급여 합계를 미리보기 후 명시적으로 반영; 기존 월정산 작성 중에만 가능 |
| FLEX API·API 토큰·OAuth·SSO | HR 가져오기/동기화·설정 흐름 없음 |
| 금융기관·카드사·영수증 OCR | 없음 |
| 국세청·지방세·4대보험 EDI·은행 지급 | 없음 |
| 회계 ERP | 없음 |
| 전자서명·서명 본인인증 | 없음. 외부 체결 사실을 사용자가 기록 |
| 이메일·SMS·모바일 푸시·Slack | HR 명령에서 발송하는 연결 없음. 화면 저장 알림은 외부 발송과 다름 |

| 음성 녹음·녹취·AI 요약 | 없음 |

이 표는 이번 HR 모듈의 업무 연결을 설명한다. 기존 ODA의 다른 모듈에 별도 기능이 있는지와 혼동하지 않는다. 코드에 URL·금액·텍스트 보관 위치를 저장하는 것만으로 외부 시스템 연동을 주장하지 않는다.
