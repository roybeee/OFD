# OFD·ODA 서버 자원 공용 검토

검토일: 2026-09-14. 검토 대상은 이 저장소의 OFD V2와 ODA 개발본이다. **인프라는 공용으로 쓸 수 있으나, 앱과 데이터베이스·계정은 분리하는 구성이 적절하다. 현재 운영 서버의 남는 용량이 충분하다는 판정은 아직 할 수 없다.**

Render 연결 상태는 확인했지만 이 실행에 서비스 조회 기능이 노출되지 않아 실제 서버 사양·사용량·요금을 조회하지 못했다. 아래 사양은 소스의 설정안이며 운영 서버 실측값이 아니다. 이번 검토로 운영 설정을 변경하거나 배포하지 않았다.

## 공용 범위별 판단

| 구성 | 판단 | 적용 조건 |
|---|---|---|
| 같은 Render 워크스페이스·지역 | 가능 | 관리와 내부 네트워크를 함께 사용. 별도 서비스에 설정된 CPU·RAM이 자동으로 공동 용량이 되는 것은 아님 |
| 같은 PostgreSQL 인스턴스, OFD·ODA 별도 DB와 사용자 | 조건부 가능 | 다른 DB에 접근할 수 없도록 권한 검증, 합산 저장공간·메모리·연결수 점검, DB별 복구 검증 |
| 같은 DB의 별도 schema | 현재 바로 적용 불가 | 모든 연결 풀·마이그레이션·작업 큐의 schema와 권한 분리를 추가 구현해야 함 |
| 같은 DB의 같은 테이블 | 현재 적용 비권장 | 브랜드별 권한과 작업 큐 분리가 없어 서로의 데이터·작업에 영향을 줄 수 있음 |
| 직접 관리하는 한 VM에 별도 컨테이너 | 조건부 가능 | ODA 전용 DB·네트워크·키, CPU·메모리 제한, 독립 재시작과 백업. 호스트 장애 영향은 함께 받음 |

Render는 같은 워크스페이스·지역의 서비스 간 내부 통신을 지원한다. [Render Private Network](https://render.com/docs/private-network)

PostgreSQL 인스턴스 하나에 여러 데이터베이스를 만드는 것도 지원한다. 다만 데이터베이스를 나누어도 호스트 장애와 자원 경합까지 분리되는 것은 아니다. [Render Postgres 다중 데이터베이스 안내](https://render.com/docs/postgresql-creating-connecting#adding-multiple-databases-to-a-single-instance)

## 확인한 설정과 코드

`render.yaml`과 `render.oda.yaml`에는 각각 다음 구성이 적혀 있다.

| 구성 요소 | 소스의 설정 |
|---|---|
| 웹 | `starter`, Singapore |
| API | `standard`, Singapore |
| 백그라운드 worker | `starter`, Singapore |
| PostgreSQL | `basic-256mb`, 디스크 1GB, 자동 확장 꺼짐, 연결 풀링 서비스 없음 |

저장소에는 별도로 `server/`의 Node.js·SQLite 서버판도 있다. 실제 OFD가 이 서버판을 사용한다면 위 Render 사양이 해당 서버를 설명하지 않는다. 이 경우 ODA는 별도 PostgreSQL을 필요로 하며 OFD의 SQLite 파일을 재사용할 수 없다. 실제 OFD 서비스와 실행 버전을 먼저 대조해야 한다.

현재 ODA는 `WORKSTATION_BRAND`로 화면을 구분하지만 데이터 접근을 브랜드별로 분리하지 않는다. 매장 단위 권한은 있으나 본사 마스터와 전체 매장 재무 계정의 접근 범위, 본사 사업자 선택은 브랜드별로 나뉘지 않는다. 초기 등록도 비어 있는 전용 DB를 전제로 한다. 따라서 OFD의 `DATABASE_URL`을 ODA에 그대로 복사하면 안 된다.

worker 역시 브랜드 구분 없이 동일한 outbox에서 작업을 가져온다. OFD·ODA worker가 같은 테이블에 연결되면 서로의 외부 처리 작업을 가져오거나 준비 상태를 잘못 판단할 수 있다. 별도 DB를 쓰면 작업 큐와 감사 기록도 분리된다.

근거 파일: `apps/api/src/oda-routes.ts`, `service.ts`, `auth-service.ts`, `oda-provisioning.ts`, `apps/worker/src/worker.ts`, `packages/db/src/postgres-repository.ts`.

## 저장공간과 처리 부하

ODA는 현재 매장·월별 최대 10MiB, 파일별 최대 2MiB, 정산 내역 5,000행을 허용한다. 증빙 원본을 DB의 월 정산 JSON 안에 base64로 보관하므로 **원본 10MiB는 인코딩 후 약 13.33MiB**가 된다.

아래는 실제 사용 예측이 아니라 파일 저장 방식의 산술 예시다. 12개월 보관을 가정한다.

| 매장 수 | 매장당 월 원본 파일 | 연간 base64 데이터량 |
|---|---:|---:|
| 1개 | 1MiB | 약 16MiB |
| 10개 | 1MiB | 약 160MiB |
| 10개 | 10MiB, 현재 상한 | 약 1.56GiB |
| 30개 | 10MiB, 현재 상한 | 약 4.69GiB |

거래내역·확정본·감사 이력·인덱스·WAL과 기존 OFD 데이터는 위 계산에서 제외했다. PostgreSQL 압축과 정리 상태에 따라 실제 디스크 점유량은 달라지므로 base64 크기를 그대로 청구 용량으로 보면 안 된다. 별도 백업 보관 공간도 계산해야 한다.

거래 한 건의 분류·확인 상태를 수정해도 월 정산 JSON 전체가 갱신된다. 새 월을 열거나 전월 반복비용을 제안할 때 과거 월 자료를 원본 바이트까지 읽는 경로도 있다. 누적 기간과 동시 접속이 늘면 API 메모리와 DB 입출력이 증가한다. 감사 로그에 원본 파일 자체가 매번 복사되는 구조는 아니다.

공용 운영 전 우선 개선 대상은 다음과 같다.

1. 증빙 원본을 비공개 객체 저장소로 옮기고 DB에는 크기·해시·소유 매장·원본 위치만 보관한다. 다운로드 권한 확인과 백업 일관성은 유지한다. **현재 개발본에는 이 이전을 구현하지 않았다.**
2. 전월 기준·반복비용 조회를 필요한 필드와 대상 월만 가져오도록 변경한다.
3. 실제 월마감 파일을 사용해 동시 업로드·정산 확정·엑셀 출력을 시험하고 OFD의 응답시간 변화를 확인한다.

DB 연결수도 별도로 제한해야 한다. 현재 기본값의 잠재 상한은 API 30개(주 저장소 20 + POS 3 + 개점 2 + 현장 5), worker 23개(주 저장소 20 + 필요 시 POS 3)다. 두 스택이면 약 106개이며 배포 중 구·신 프로세스나 관리 연결은 별도다. 모든 연결이 항상 사용된다는 뜻은 아니다. `DB_POOL_MAX` 변경은 주 저장소뿐 아니라 현장 풀에도 적용되므로 합산해서 검토해야 한다.

Render의 현행 8GB 미만 PostgreSQL 플랜은 최대 연결수 100개로 안내된다. 실제 서버의 플랜·연결 한도를 대조하고 풀 상한과 대기 시간을 함께 조정해야 한다. [Render 연결 한도](https://render.com/docs/postgresql-creating-connecting#connection-limits)

## 권장 구성과 최종 용량 판정

**같은 Render 워크스페이스에 ODA 앱을 별도로 운영하고, 기존 PostgreSQL 인스턴스의 여유가 검증되면 그 안에 ODA 전용 DB·사용자를 추가하는 안**을 우선 비교한다. ODA 세션·암호화 키, 도메인, 외부 연동 자격증명도 분리한다. DB 공용이 OFD의 응답시간이나 복구 목표를 해치면 ODA DB 인스턴스를 별도로 둔다.

같은 워크스페이스에 서비스를 추가하는 것만으로 서버 비용이 없어지지는 않는다. DB 인스턴스를 공유하면 별도 DB 인스턴스 비용을 줄일 가능성이 있지만, 필요한 증설과 별도 앱 비용을 합산해야 한다. 운영 요금제와 실사용량이 없으므로 이번 검토에서는 금액 절감을 확정하지 않는다.

최종 판단에는 아래 실측 자료가 필요하다. 서버 운영자가 한 번 수집하는 자료이며 매장에 매월 입력하도록 요구하는 항목이 아니다.

| 확인 항목 | 판단에 사용할 자료 |
|---|---|
| 실제 OFD 구성 | 서비스 이름, 실행 버전, CPU·RAM·디스크 사양, 현재 DB 종류와 요금제 |
| 평소·월마감 부하 | 가용 기간의 CPU·메모리, 디스크 사용/입출력, DB 활성 연결, OFD 오류율·응답시간. 월마감 구간이 없으면 별도 부하 시험 |
| ODA 예상량 | 매장 수, 매장당 월 파일 크기·거래 행 수, 동시 사용자 수, 보관 기간 |
| 장애 복구 | OFD에 영향을 주지 않는 ODA 재시작, DB별 백업·복구와 권한 분리 검증 |

Render Metrics에서 CPU·메모리·디스크·활성 연결을 확인할 수 있다. HTTP 지표는 서비스 종류·플랜에 따라 달라지며 내부 API 요청은 공개 웹 요청 통계에 포함되지 않을 수 있다. [Render Service Metrics](https://render.com/docs/service-metrics)

초기 운영 여유 기준으로는 합산 피크 CPU 약 70% 이하, 활성 연결 한도의 약 70% 이하, 향후 12개월 증가분과 유지보수 공간을 포함한 디스크 점유율 약 70% 이하를 검토한다. 이는 이 프로젝트의 잠정 기준이지 Render의 보장치나 충분조건이 아니다. 메모리는 캐시를 구분해 여유를 확인하고, 메모리 부족 재시작·스왑 증가가 없어야 한다. OFD의 기존 응답시간·오류율이 유지되는지 시험으로 확인해야 한다.

디스크가 가득 차면 Render가 DB를 중지할 수 있으므로 1GB 설정을 그대로 공용화하지 않는다. 실사용량을 확인해 필요한 용량과 경보·확장 설정을 정한다. [Render 저장공간 부족 시 동작](https://render.com/docs/postgresql-creating-connecting#running-out-of-storage)

**현 단계 결정:** 인프라 공용안은 채택 후보, 동일 테이블 공용안은 제외. 현재 서버의 무증설 수용 가능 여부와 최종 비용은 실측 후 결정한다. 기존 OFD 운영 환경은 이번 검토에서 변경하지 않았다.
