# ODA 워크스테이션 1차 개발

OFD V2의 React PWA, Fastify 로그인·역할 권한, PostgreSQL 저장소, 감사 로그, 발주·입고·매출·계정 관리 구조를 재사용한다. ODA 월 손익과 운영계약 이익배분은 기존 식자재 공급대금 정산과 별도 원장으로 관리한다. OFD 원본 계약서/브랜드 자료는 ODA 정산 자료로 배포하지 않는다.

## 매장 사용 흐름

1. 일회성 설정 키와 본인의 이름·이메일·비밀번호로 **마스터 계정만 등록**한다. 사업자·실제 매장·A·B 정보는 첫 가입에 필요하지 않다. 마스터 홈에서 사업자 정보가 비어 있는 `ODA 기본 작업공간`을 선택해 기능을 사용할 수 있다.
2. 필요한 시점에 **매장 관리**에서 실제 매장을 추가하거나 작업공간 이름을 바꾸고, 사업자 정보를 등록한다. **계정 관리**에서는 실제 A·B 담당자를 해당 매장에 배정한다. 사업자 미등록 상태에서도 자료 업로드·손익 검토·초안 정산서 출력·관리 기능을 사용할 수 있다.
3. **정산 기준**에서 부가세 포함/제외, POS의 배달 매출 포함 여부, B 정산금 부가세, 귀속 기준과 계약 보완사항을 입력한다. 실제 A·B가 각자 로그인해 동일 기준을 확인한다. 이후 기준을 바꾸면 확인이 해제된다. 마스터의 운영 권한으로 A·B의 개별 확인을 대신하지 않는다.
4. 매월 POS/배달 월마감, 비용 명세, 사업용 계좌 자료를 XLSX 또는 CSV로 넣는다. PDF·영수증 사진은 근거 자료로 첨부한다. 사진/PDF 자동 인식은 제공하지 않는다. 원본 파일과 원본 행 번호가 보존된다.
5. 자동 분류된 결과에서 누락·중복·미분류만 확인한다. 은행 입출금은 대사용이며 매출/비용에 자동 이중 반영하지 않는다. 반복비용은 전월 자료를 제안하되 확인 후 반영한다.
6. **월 정산**에서 운영손익, A 선배분, 잔여 5:5, B 부가세와 지급액을 확인한다. A는 익월 5일까지 정산서를 확정하고 B는 같은 내역·증빙을 열람하고 의견을 남긴다. 마스터도 정산 확정·재개방·지급 기록을 처리할 수 있으나, A·B의 기준 확인과 미해결 정산 항목 검사를 통과해야 한다. B의 매월 승인은 계약 의무가 아니며 기준 확인과 구분한다.
7. 실제 송금 후 익월 10일 지급 정보를 기록한다. 앱의 지급완료 버튼은 은행 이체를 실행하지 않는다. 확정본을 수정하려면 사유를 남겨 새 초안을 열며 과거 확정본은 보존된다.
8. **엑셀 정산서**에서 월손익·배분, 거래내역, 증빙목록, 기준·확인, 변경이력 5개 시트를 내려받는다. 초안은 초안으로 표시하며, 확정·지급 기록은 보관된 확정본의 계산값을 사용한다. 미합의 금액은 임의 숫자를 넣지 않는다.

## 마스터의 월별 정산 확인

마스터 홈의 **매장별 월 정산 현황**은 지난달을 기본으로 표시한다. 월을 바꾸면 각 매장의 상태·매출·운영비·영업이익·B 예상 지급액과 다음 할 일을 한 화면에서 확인한다. 기한을 넘긴 정산·지급은 날짜와 함께 표시하며, 다음 할 일 버튼은 같은 매장·같은 정산월의 해당 화면으로 연결된다. 이번 달 자료 입력은 상단의 별도 버튼을 이용한다.

자료가 없는 달은 0원으로 간주하지 않고 `자료 미등록`과 `—`로 표시한다. 작성 중 금액은 부가세 기준과 잠정 여부를 표시하고, 확정·지급된 금액은 보관된 확정본을 사용한다. 조회만으로 빈 정산월을 생성하지 않는다. 현황은 한 페이지에 20개 매장이며, 원본 파일 bytes와 과거 거래 복사본을 API로 전송하지 않는다. 매장 범위와 비활성 매장 제외 조건은 서버에서 적용한다.

## 매장별 엑셀 양식 재사용

정상 반영한 XLSX의 제목 행·시트 선택·열 연결은 ODA DB에 매장과 자료 종류·출처별로 기억한다. 같은 매장을 담당하는 사용자는 다른 PC에서도 다음 달 업로드에 재사용한다. 열 제목과 순서가 모두 일치할 때만 저장한 열 연결을 자동 적용하며, 미리보기 확인 후 직접 반영하는 절차는 유지한다. 양식이 바뀌면 시트·제목 행 또는 열 연결을 수정해 다시 확인한다.

미리보기·오류·중복 거절은 저장한 양식을 변경하지 않는다. 원본 반영과 양식 저장은 같은 트랜잭션으로 처리한다. 저장에는 파일 내용이나 거래 금액을 복제하지 않으며, 변경자와 설정 변경 이력을 남긴다. 매장 밖의 양식은 조회할 수 없고 감사자는 초기화할 수 없다. `저장한 양식 초기화`는 해당 매장·출처의 다음 업로드부터 적용되며 기존 거래나 이미 열린 미리보기에는 영향을 주지 않는다. 서버 초기화 뒤에는 다른 브라우저의 오래된 설정도 되살리지 않는다.

서버 설정을 읽는 동안 업로드를 잠시 막는다. 읽기에 실패하면 오류와 재시도 버튼을 표시하고 기본 설정으로 수동 확인할 수 있다. 과거 브라우저 설정은 서버에 저장·초기화 이력이 없을 때만 이어받고, 다음 정상 반영 때 서버에 저장한다.

## 계약 적용

- 운영이익 = 월 매출 − 운영비. A 선배분 300만원, 감가상각, B 배분금은 운영비에서 제외한다.
- 운영이익 1,000만원인 경우 A 650만원, B 350만원. 부가세 10% 별도 가산을 확인한 경우 B 지급액 385만원. B 지급액을 운영비에 다시 넣지 않는다.
- 이익 300만원 미만·적자·월중 개업/종료는 계약 공백을 자동 해석하지 않는다. 확인되지 않은 예외는 확정을 막고 합의 대상으로 표시한다.
- 제9조의 잘못된 조문 참조와 월 정산 적용 범위는 별도 확인한다. 앱의 설정 확인은 계약서 자체의 법률적 보완이나 세금계산서 발행이 아니다.
- 매출/비용 세액은 입력 자료의 값을 사용한다. 부가세 제외 기준에서 세액이 없으면 1.1로 임의 역산하지 않는다.
- 사업용 계좌 이체, 보증금, 투자/시설비는 운영비와 분리한다. 통상 운영 외 100만원 이상 투자에는 사전 동의 근거를 남긴다.

## 실행과 배포

기본 사용 환경은 [온라인 ODA 워크스테이션](https://oda-web-wpts.onrender.com)이다. 현재 구성은 `render.oda.shared.yaml`이며, OFD와 같은 PostgreSQL 호스트에서 `oda_production` DB와 `oda_app` 운영 계정을 별도로 사용한다. 웹 최종 배포·접속 확인을 포함한 최신 운영 상태는 [공용 서버 배포 기록](oda-shared-deployment.md)을 따른다. 첫 설정에서는 일회성 키와 실제 마스터의 이름·이메일·비밀번호만 등록한다. 사업자·매장·A·B 계정은 로그인 후 필요에 따라 추가한다.

Mac에서 전용 PostgreSQL에 저장하는 로컬 실행도 별도 선택할 수 있다. Docker Desktop 준비 후 `Start-ODA.command`를 열면 최초 등록 화면에서 마스터만 등록하거나 기존 전체 정보 등록 방식을 선택할 수 있다. 종료는 `Stop-ODA.command`, 백업은 `Backup-ODA.command`다. 자세한 전제조건과 범위는 [로컬 실행 안내](oda-local.md)를 따른다. Mac 실기기의 Docker Desktop 기동·재시작·백업 복구 최종 검증은 아직 완료하지 않았다.

아래 개발 명령은 로컬 저장 실행기와 별개인 메모리 테스트 모드다.

```bash
npm ci
npm run dev:oda
```

개발 화면은 `http://localhost:5173/store/oda-settlement`. 명확히 표시되는 테스트 모드이며 종료하면 초기화된다. 실제 매장 자료 입력용이 아니다. 운영 배포는 ODA 전용 PostgreSQL 데이터베이스가 필수이며 메모리 저장·테스트 인증을 허용하지 않는다.

```bash
npm run build:oda
```

- 현재 공용 구성은 `render.oda.shared.yaml`이다. ODA 웹·API만 생성하며, 원본 증빙은 ODA DB에 보존한다. `ODA_SETTLEMENT_ONLY=true` 프로필은 외부 공급자·메일·worker를 비활성화하고 지원하지 않는 API를 차단한다.
- PostgreSQL의 실제 역할 분리 검사 후 `ofd_app/ofd_postgres`와 `oda_app/oda_production`의 자기 DB 연결 및 상대 DB 연결 거절을 확인했다. 공용 호스트의 용량·장애까지 독립적인 것은 아니다. [공용 운영 검토](oda-shared-hosting-review.md)와 [적용 기록](oda-shared-deployment.md)을 참고한다.
- 웹은 `infra/docker/oda-web.Dockerfile`, API는 `infra/docker/api.Dockerfile`을 사용한다. ODA 전용 세션·암호화 키와 HTTPS 주소를 설정한다.
- 독립 인프라 대안 `render.oda.yaml`은 웹·API·worker·PostgreSQL을 별도로 구성하는 기존 전체 운영안이다. 현재 월 정산 전용 온라인 프로필과 구분하며, 전체 운영안의 공급자·저장소 요건은 `docs/deployment-v2.md`를 따른다.
- 온라인 첫 설정은 마스터 단독 등록이 기본이다. 이후 마스터 홈의 매장·계정 관리에서 실제 매장과 선택적인 사업자 정보, 실제 A·B 담당자를 추가한다. A·B가 계약 기준을 확인할 때는 각자의 계정과 매장 배정을 사용한다. 기존 전체 정보 등록 및 운영자용 CLI 대안은 아래에 별도로 안내한다.
- 외부 POS·배달·은행 계정의 실시간 연결을 새로 완료한 것은 아니다. 1차의 입력 방법은 파일 업로드다. 실제 업체별 파일의 열 이름이 다르면 업로드 미리보기의 열 매핑을 사용한다.
- 자동 이체·전자세금계산서 발급은 이 월 정산 기능에서 실행하지 않는다. 계산/증빙/확정/지급 기록을 제공한다.

## 보존과 검증

원본 업로드는 크기가 제한된 비공개 정산 저장 레코드에 보존하며 조회 목록에서 파일 바이트는 제거한다. 원본 다운로드는 로그인·매장 권한을 재검사한다. 변경 시 낙관적 버전검사와 서버의 직렬화 잠금으로 동시 수정을 방지한다. 확정 스냅샷·수정 사유·작성자·시각은 저장된다. 이는 애플리케이션 수준 감사 이력이며 외부 공증이나 관리자까지 방어하는 불변 원장을 의미하지 않는다.

### ODA 첫 매장과 A·B 계정 등록

온라인 첫 설정 화면의 **마스터 계정만 등록**이 기본 방법이다. 이 제목의 매장·A·B 등록은 가입 후 선택하는 후속 작업이다.

1. 운영 관리자가 Render의 `oda-production-secrets` 환경그룹에서 `ODA_SETUP_TOKEN`을 확인하고, ODA 첫 설정 화면의 비밀번호 형태 입력란에 입력한다. 키 값은 문서·Git·채팅에 기록하지 않는다.
2. 본인의 이름·로그인 이메일·비밀번호를 입력한다. 비밀번호는 숫자·특수문자를 포함한 12자 이상이다. 사업자등록번호나 A·B 정보를 먼저 입력하지 않아도 된다.
3. ODA 전용 온라인 저장 안내와 입력 내용을 확인한 뒤 등록한다. 서버는 설정 키·만료·정확한 HTTPS 출처·비어 있는 DB를 검사하고 동시 중복 등록을 막는다. **본인이 직접 정한 마스터 비밀번호는 첫 로그인 때 변경을 강제하지 않는다.**
4. 마스터 홈으로 이동한다. `ODA 기본 작업공간`은 정산 자료를 정리하는 논리적인 공간이며, 실제 사업자나 가상의 계약 당사자로 등록하지 않는다. 사업자 7개 항목은 모두 빈 값으로 시작하고 `odaWorkspace` 표시로 구분한다. 법인·A·B 계정은 자동 생성하지 않는다.
5. 필요하면 매장 이름만으로 새 작업공간을 만들거나 실제 매장·사업자 정보를 추가한다. 사업자 정보는 제공할 때 전체 항목을 검증하며, 매장·계정 변경에는 최근 비밀번호 재확인이 필요하다. 계약 기준 확인에 참여할 실제 A·B 계정은 계정 관리에서 만들고 해당 매장에 배정한다.

현재 발급한 설정 키의 사용 기한은 **2026-09-16 21:48 UTC(한국 시간 9월 17일 06:48)**다. 키가 갱신되면 Render의 `ODA_SETUP_EXPIRES_AT`와 화면의 기한을 기준으로 한다. 만료되면 운영자가 새 키를 발급해야 하며, 이미 초기화한 DB에는 같은 키를 재사용할 수 없다. 초기 등록 완료 후 설정 키를 제거해도 기존 계정의 로그인과 서버 재시작은 정상 동작한다. 설정 키는 요청 헤더로만 전달하며, 설정 링크의 fragment로 받은 경우에도 화면이 즉시 주소에서 제거한다.

계약서의 당사자란은 공란이므로 회사명·당사자를 앱이 추정하지 않는다. 기본 작업공간에는 사업자 정보를 넣지 않으며, 실제 사업자·담당자 정보는 사용자가 나중에 입력한다. 마스터가 정산을 확정하거나 지급 정보를 기록할 수 있어도 실제 A·B의 기준 확인을 자동으로 채우거나 대신 승인하지 않는다.

#### 기존 전체 정보 등록 방식

사업자·실제 매장·관리자·A·B를 처음부터 함께 등록하는 이전 방식도 선택적으로 유지한다. 각 계정은 서로 다른 이메일로 생성하며, 이 방식으로 발급한 초기 비밀번호는 첫 로그인 때 변경해야 한다. 마스터 단독 등록은 본인 비밀번호를 직접 정한다는 점에서 구분한다.

#### 운영자용 CLI 대안

아래 CLI는 기존 전체 정보 등록의 대안이다. 온라인 화면을 대신해 운영자가 사업자·매장·A·B까지 한 번에 초기화해야 할 때만 사용한다. 운영 마이그레이션 후 비어 있는 ODA 전용 DB를 대상으로 `infra/oda-setup.example.json`을 복사하여 실제 본사·A 사업자 정보와 관리자/A/B의 이름·이메일을 입력한다. 개인정보가 들어간 실제 설정 파일은 Git에 저장하지 않는다.

서버 비밀값에 `ODA_MASTER_PASSWORD`, `ODA_OPERATOR_PASSWORD`, `ODA_PARTNER_PASSWORD`를 각각 12자 이상, 숫자·특수문자를 포함해 설정하고, 운영 컨테이너에서 `node apps/api/dist/bootstrap-oda.js /보안경로/oda-setup.json`을 한 번 실행한다. 이후 세 비밀값을 제거한다. 기존 데이터가 하나라도 있으면 이 스크립트는 중단한다. A와 B는 서로 다른 계정이며 모두 해당 매장에 배정된다. 최초 로그인 시 초기 비밀번호 변경이 필수다. 이미 초기화한 환경은 계정 관리에서 매장 배정이 가능한 지원 파트너 B(재무) 계정을 추가한다.

본사만 초기화하는 OFD 공용 흐름을 사용할 때도 운영 컨테이너에서는 `node apps/api/dist/bootstrap-admin.js`를 사용한다. 운영 이미지에는 개발용 tsx가 없으므로 npm 개발 명령을 실행하지 않는다.

## 이번 개발본 검증 범위

- 선행 배포본은 GitHub 브랜치 `agent/oda-workstation-release`의 앱 커밋 `60ea2ec`다. [V2 검사 실행 34900598013](https://github.com/roybeee/OFD/actions/runs/34900598013)의 quality gate에서 자동 테스트 514개 통과, ODA 전용 네이티브 통합 검사 1개 건너뛰기를 확인했다. 건너뛴 검사는 통과한 것으로 세지 않는다. 마스터 단독 등록 변경 이후의 최종 CI·배포 결과는 [최신 적용 기록](oda-shared-deployment.md)을 따른다.
- 같은 CI에서 실제 PostgreSQL smoke와 브라우저 E2E 안전 검사 3개·매장 흐름 검사 3개가 모두 통과했다. 초기 등록·업로드·정산·계정·격리 관련 로컬 검사와 ODA 빌드도 수행했다.
- 배포 전에 실제 PostgreSQL의 임시 DB·역할로 소유권·ACL 분리 검사를 통과했고 임시 자원을 정리했다. 운영 서버에서는 OFD·ODA 각각 자기 DB 접속 성공과 상대 DB 접속 거절(SQLSTATE 42501)을 확인했다. 이 검사는 별도로 건너뛴 ODA 네이티브 통합 검사를 대체했다고 표현하지 않는다.
- OFD API와 worker가 새 분리 운영 역할로 배포되어 live 상태임을 확인했다. ODA API도 live이며 마이그레이션 11개 적용을 확인했다. ODA 웹의 최종 배포·외부 접속 확인과 이후 변경 사항은 [공용 서버 적용 기록](oda-shared-deployment.md)에 기록한다.
- 이전 개발본에 포함된 PGlite PostgreSQL WASM 지속성 검증 도구도 보존했다. 이전 기록의 정상 종료·재시작 검증은 네이티브 PostgreSQL 동시성·TLS·장애복구·운영 백업 검증을 대체하지 않는다. 재현 방법은 `infra/testing/pglite/README.md`를 따른다.
- Mac 실기기의 Docker Desktop 설치·기동·재시작·백업 복구와 매장 담당자의 실제 기기 사용 검증은 미완료다. CI 브라우저 검사를 전체 실기기 검증으로 표시하지 않는다.
- 실제 POS·배달·은행 업체의 원본 파일 호환성은 대상 매장 자료로 추가 확인해야 한다.
- 앱 소스 업로드·기존 GitHub CI 실행·Render 서비스 조회와 배포를 실제 수행했다. 추가 ODA 전용 workflow 업로드는 Workflows 쓰기 권한 부족으로 보류했으며, 이를 기존 V2 CI 실행 여부와 구분한다.

ODA 기능만 재검증할 때는 `npm run test:oda`를 실행한다. 전체 자동 테스트는 `npm test`, ODA 빌드는 `npm run build:oda`다.

실제 PostgreSQL ODA 검증은 외부 운영 DB 대신 로컬의 `oda_integration_test` DB를 준비하고 `ODA_TEST_DATABASE_URL`을 설정한 뒤 `npm exec -w @ofd/api -- vitest run src/oda-postgres.integration.test.ts`로 실행한다. 기존 `DATABASE_URL`은 해당 테스트에서 사용하지 않는다.

## 보존한 업로드 개선

- 업로드 파일을 추가하거나 자료 유형·탭을 바꿔도 기존 대기목록을 유지한다.
- 여러 자료의 읽기·저장 진행률을 표시하고, 오류 파일을 개별 제거하거나 정상 파일만 명시적으로 반영할 수 있다.
- 성공적으로 반영한 엑셀 양식 설정을 매장·출처별로 기억한다. 열 구성이 일치하는 자료에서만 저장한 매핑을 다시 사용한다. 거래 내역과 비밀번호는 이 설정에 저장하지 않는다.
- 첫 화면에 누락 자료·확인할 거래·남은 정산 기준을 표시한다.
- 제외한 통장 입출금·플랫폼 예정입금은 대사 합계에서도 빠진다.
- 제외한 플랫폼 수수료·예정입금은 제외 전 유형·분류로 복원되어 매출로 잘못 더해지지 않는다.
- 개발용 `npm run dev:oda`는 API 준비 후 화면을 실행하며, 포트 충돌과 실행 실패를 알린다. 테스트 실행이 운영 DB를 선택하지 않도록 분리한다. `Start-ODA.command`는 이번 개발에서 전용 PostgreSQL 로컬 저장 실행으로 전환했다.
- 작업 브랜치에는 ODA 전용 CI `.github/workflows/oda.yml` 제안을 보존했다. 배포 브랜치는 기존 GitHub workflow를 유지하며, 확인한 원격 검사 결과는 위 V2 실행 기록을 기준으로 한다.
